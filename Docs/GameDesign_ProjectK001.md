# Project K — 게임 기획서

> **문서 목적**: 신규 프로젝트의 세부 기획을 파생시키기 위한 현행 설계 기록.
> 모든 수치는 2026-08-25 기준 코드에서 직접 추출했다.
> 각 절 끝의 `정본:` 표기는 그 수치가 실제로 사는 파일이다 — 코드와 문서가 어긋나면 코드가 맞다.

## 0. 한 줄 요약

**30스테이지를 순차로 돌파하는 2D 오토배틀 로그라이트.**
전투는 전부 자동으로 흐르고, 플레이어의 의사결정은 *전투 사이*에 몰려 있다.
한 판(런)이 끝나면 **환생**해서 영구 성장 통화를 회수하고 다시 시작한다.

| 축 | 설계 |
|---|---|
| 코어 루프 | 전투(자동) → 보상 선택 → 정비 → 다음 스테이지 |
| 메타 루프 | 런 실패/종료 → 환생 포인트 → 유물 트리 → 더 강한 시작점 |
| 플레이어 조작 | 장수 선택 · 어빌리티 선택 · 장비 · 특성 · 배속 — **전투 중 직접 조작 없음** |
| 실패 처리 | 패배 = 즉시 런 종료. 이어하기 없음 |

## 1. 게임의 형태

### 1.1 장르 정의

**2D 전술 배틀 / 오토배틀 (Auto-battler) + 로그라이트 메타 성장.**

전투는 플레이어가 조작하지 않는다. 장수와 병사가 스스로 타겟을 찾고, 이동하고, 공격하고, 스킬을 쓴다.
플레이어가 하는 일은 **전투에 들어가기 전에 판을 짜는 것**이다.

> 이 구조를 고른 이유: 화면에 유닛이 수백~1,000마리 단위로 깔린다. 개별 조작이 성립하지 않는
> 밀도이며, 그 밀도 자체가 볼거리다. "내가 조립한 부대가 알아서 이긴다"가 보상이 된다.

### 1.2 화면 구성

| 씬 | 캔버스 | 역할 |
|---|---|---|
| Splash | — | 부팅·데이터 로드 |
| Lobby | **1920×1080 가로** | 장수 선택 · 출전 준비 · 상점 · 이벤트 · 유물 · 도감 |
| InGame | **1080×1920 세로** | 전투 |

**두 씬은 동시에 상주한다.** 전투에 들어가도 로비를 언로드하지 않고, 반대도 마찬가지다.
씬 로드가 없어 전환이 즉시 일어나고, 로비 배경에 실제 전장을 비추는 연출(데모 전투)이 가능하다.

> ⚠ 대부분의 팝업은 로비 위에 뜬다 → **세로 여유가 1080px 뿐**이다.
> 팝업 높이를 고정하면 잘린다. 세로 스트레치 + 가변 영역으로 만든다.

정본: `Lobby/SceneDirector.cs`, `InGame/Battle/BattleArena.cs`

## 2. 코어 루프

### 2.1 한 런의 구조 — 30스테이지 고정 시퀀스

런은 **30개의 스테이지를 순서대로** 지난다. 갈림길도, 선택도 없다.
루트 선택이 없는 대신 **각 스테이지에서 무엇을 얻을지**에 결정이 몰려 있다.

**시퀀스 생성 규칙** (런 시작 시 1회 확정, 세이브에 저장)

| 규칙 | 배치 |
|---|---|
| 1~2 스테이지 | **항상 일반** (고정) |
| 5의 배수 (5·10·15·20·25·30) | **엘리트 = 허들** |
| 허들 바로 앞 (4·9·14·19·24·29) | **상점** |
| 이벤트 | 10개를 2~4 스테이지 간격으로 고르게 배치 |

**결과 구성 (30칸)**: 일반 8 · 상점 6 · 엘리트 6 · 이벤트 10

**설계 의도**
- **1~2를 일반으로 고정**: 런 시작(신규·환생 직후) 직후 로비에 들어서자마자 상점/이벤트 팝업이
  자동으로 뜨면 상황 파악이 안 된다. 첫 판은 전투로 시작해야 한다.
  2스테이지는 로비 튜토리얼이 도는 칸이라 팝업이 끼면 안내가 가려진다.
- **상점을 허들 직전에 고정**: 허들은 스탯 배율이 뛰는 관문이다. 그 앞에서 반드시 한 번
  정비할 수 있어야 한다. 무작위로 뿌리면 상점이 허들 *직후*에 몰려 정작 필요할 때 빈손이 된다.
- **이벤트를 간격으로 배치**: 무작위로 뿌리면 두 칸 연속으로 붙거나 8스테이지 넘게 안 나온다.
  이벤트는 특성·용병을 얻는 거의 유일한 칸이라 "언제 또 나오나"가 예측돼야 계획이 선다.

정본: `Data/Stage/RunSequenceGenerator.cs`

### 2.2 스테이지 타입 4종

| 타입 | 내용 |
|---|---|
| **Normal** | 일반 전투. 웨이브를 전부 클리어하면 승리 |
| **Elite** (허들) | 스탯 배율 ×1.15 추가 · 웨이브당 적 +8 · 웨이브 +2. 보스 등장 |
| **Shop** | 로비 도착 시 `RunShopPopup` 자동 오픈. 장비·용병·특성 구매 |
| **Event** | 로비 도착 시 `EventPopup` 자동 오픈. 선택지형 텍스트 이벤트 |

> ⚠ **상점도 이벤트를 거쳐 열린다.** `Shop` 칸은 "행상인의 좌판" 이벤트를 띄우고,
> 거기서 "상품을 본다"를 고르면 `RunShopPopup`이 이어 열린다.
> 상점을 그냥 화면으로 띄우지 않고 한 겹 감싼 이유는 톤 일관성이다 — 모든 비전투 칸이
> 같은 문법(텍스트 + 선택지)으로 들어온다.

자동 오픈은 **스테이지당 1회**만 (`AutoPopupShownStage`를 세이브에 기록). 탭을 오갈 때마다 다시 뜨면 안 된다.

정본: `UI/Lobby/StageSelectUI.cs`, `Data/Sections/StageProgressData.cs`

### 2.3 전투 흐름

```
출전 → 아군 스폰(대기) → [웨이브 1 … N] → 전멸 판정 → 승리/패배
                              ↓
                        웨이브 클리어 시 보상
```

- 웨이브 수: **2~8** (허들은 +2)
- 웨이브당 적 수: **6~100** (허들은 +8, 난이도 물량 보너스 적용)
- 동시 유닛 상한: **1,000마리** — 그 이상은 프레임이 먼저 무너진다
- 패배 조건: **아군 전멸**
- 패배 = 런 종료. 이어하기 없음 → 환생 화면으로 직행

정본: `InGame/Battle/BattleManager.cs`, `Data/Stage/StageConfig.cs`

### 2.4 난이도 곡선

적 스탯 배율은 **5스테이지 간격 앵커 사이를 기하 보간**한다.

```
앵커: [1.0, 2.2, 5.0, 11, 25, 55, 85]
       st1  st6  st11 st16 st21 st26 (꼬리)
스테이지당 약 ×1.17 성장
```

- **초반 완화**: 스테이지 1은 ×0.55에서 시작해 8스테이지에서 1.0으로 선형 복귀
- **허들 추가**: 5의 배수는 앵커 배율에 ×1.15 추가
  > ⚠ 1.15를 넘기지 말 것 — 스테이지당 기본 성장(≈1.17)보다 크게 잡으면
  > 허들 *다음* 스테이지가 오히려 쉬워진다
- 적 레벨: 스테이지 1→30에 걸쳐 1→50 선형 보간

**왜 계단이 아니라 보간인가**: 예전에는 블록 안에서 배율이 고정이었다(1~5가 전부 ×1.0).
다섯 판 내리 같은 세기의 적이 나오는데 그동안 플레이어는 레벨·장비·어빌리티로 계속 강해져
초반이 통째로 허무해졌고, 6스테이지에서 갑자기 2.5배가 튀어나와 벽처럼 느껴졌다.

정본: `Data/Stage/StageConfig.cs`

## 3. 유닛 시스템

### 3.1 유닛 계층

| 타입 | 소속 | 설명 |
|---|---|---|
| **General (장수)** | 아군 | 플레이어가 고르고 키우는 유닛. 병사를 지휘한다 |
| **Soldier (병사)** | 아군 | 장수에 종속. 장수 스탯의 비율을 물려받는다 |
| **Enemy** | 적 | 일반 적 |
| **Elite** | 적 | 강화된 적 |
| **Boss** | 적 | 허들 스테이지 우두머리 |

**병사는 독립 유닛이 아니다.** 장수가 죽으면 병사도 의미를 잃고, 병사 수·강함은 장수의
`SoldierCount` / `CommandPower` 스탯이 결정한다.

```
병사 스탯 비율 = SoldierBaseStatRatio(0.2) + CommandPower × 0.01
```

즉 지휘력 1포인트당 병사가 장수 스탯의 1%씩 더 물려받는다.

정본: `InGame/Unit/UnitComponents.cs`, `InGame/GameplayConfig.cs`

### 3.2 직업 4종

| 직업 | 정체성 | HP | 공격력 | 사거리 | 공속 | 병사 수 | 지휘력 |
|---|---|---|---|---|---|---|---|
| **Knight** (기사) | 병사 특화 · 근접 고위험 고딜 | 960~1920 | 45~100 | 0.8~1.2 | 0.9~1.9 | **3~7** | **10~45** |
| **Archer** (궁수) | 사거리 · 평타 위주 | 578~1238 | 30~70 | **5.5~9.9** | 0.9~1.9 | 1~2 | 1~30 |
| **Mage** (마법사) | 한 방이 굵다 | 446~1023 | **85~185** | 4.0~7.0 | **0.32~0.68** | 1~2 | 1~30 |
| **ShieldBearer** (방패병) | 탱킹 | **1200~3000** | 25~60 | 0.7~1.0 | 0.6~1.4 | 1~2 | 1~30 |

| 직업 | 방어율 | 치명타 확률 | 치명타 배율 | 평균 DPS |
|---|---|---|---|---|
| Knight | 0.06~0.15 | 13% | ×1.5 | ~170 |
| Archer | 0.03~0.10 | 15% | ×1.8 | ~158 |
| Mage | 0.02~0.08 | 10% | **×2.0** | ~155 |
| ShieldBearer | **0.22~0.32** | 5% | ×1.5 | ~90 (탱킹 보정) |

**설계 노트**
- 직업은 `unitName` 시드로 **결정적**으로 배정된다 — 같은 이름은 항상 같은 직업.
- 스탯은 위 범위 안에서 랜덤 롤 → 같은 직업이라도 개체차가 크다. 이것이 "장수 뽑기"의 진폭.
- **마법사 공격력 하한을 올린 이유**: 공속이 궁수의 1/3이라 공격력 하한이 낮으면
  DPS 바닥이 다른 직업보다도 아래로 내려간다. 상한은 그대로 둬서 진폭은 유지.
- **방패병 방어율 폭을 좁힌 이유**: 하한이 낮으면 "방패병인데 물렁한" 개체가 나온다.
  항상 단단하되, 장비·유물을 얹어도 실효 90%에는 쉽게 닿지 않게.

정본: `InGame/Unit/UnitJob.cs`, `InGame/GameplayConfig.cs`

### 3.4 레벨

```
필요 경험치      = 100 / 레벨
레벨업 비용(골드) = 100 + (현재레벨 - 1) × 10
레벨당 스탯      = 전 스탯 ×1.01 (승산) + HP +10 / 공격력 +1 (가산)
```

배율과 가산을 섞은 이유: 배율만 쓰면 초반 저스탯 장수의 레벨업이 체감되지 않고,
가산만 쓰면 후반에 의미가 사라진다.

정본: `InGame/GameplayConfig.cs`

### 3.6 데미지 공식

```
eff     = 방어율 ≤ 0.95 ? 방어율 : 0.95 + (방어율 - 0.95) × 0.1   // 소프트캡
defense = min(eff, 0.999)                                        // 실효 상한
defense = max(0, defense - 관통)                                  // 관통은 최종값에서 차감
피해     = max(원피해 × (1 - defense), 1)                          // 최소 1
```

**설계 노트**
- 방어율 95%를 넘으면 초과분의 10%만 반영 → 방어 스택이 무한히 강해지지 않는다.
- **관통은 소프트캡을 거친 최종 방어율에서 뺀다.** 원본 방어율에서 빼면 관통이
  소프트캡 공식을 거꾸로 타고 증폭된다.
- 최소 피해 1 보장 → 무적 유닛이 나오지 않는다.
- **쿨다운 감소 상한 80%**.

정본: `InGame/Unit/UnitHitSystem.cs` (`DamageMath.AfterDefense`)

## 4. 스킬 시스템

### 4.1 액티브 스킬 33종

장수가 쿨다운마다 자동으로 쓴다. 플레이어는 시전 타이밍을 고르지 않는다.

**일반 (1~20)** — 직업별 추첨 풀

| # | 이름 | 효과 | 직업 |
|---|---|---|---|
| 1 | 강타 | 단일 돌진 타격 + 넉백 | 방패·전사 |
| 2 | 일제 사격 | 전체 즉시 일반 공격 | 궁수·법사 |

## 6. 메타 성장 (환생해도 남음)

### 6.1 환생

**언제**: 2스테이지 이상 클리어 시 언제든 (또는 패배 시 강제)

```
환생 포인트 = Σ (스테이지별 증분) × 난이도 배율

증분 구간:
  ~9    → +1pt / 스테이지
  10~15 → +4pt
  16~20 → +8pt
  21~25 → +14pt
  26~   → +30pt

예) st30 = 1×8 + 4×6 + 8×5 + 14×5 + 30×5 = 292pt
```

**배수 곡선**: st5 ×1.0 · st10 ×1.2 · st15 ×1.5 · st20 ×2.0 · st25 ×2.5 · st30 ×3.0

> **설계 노트 — 뒤로 갈수록 가팔라야 한다**
> 예전 곡선은 st30이 98pt로, **초반에 죽고 다시 도는 쪽이 이득**이었다.
> 깊이 들어간 판이 보상받아야 "한 번 더 멀리 가 보자"가 성립한다.
> 9스테이지까지는 예전 값 그대로 — 초반 반복은 손대지 않는다.
>
> **설계 노트 — 최소 환생 스테이지를 2로 낮춘 이유**
> 예전엔 5스테이지부터였고, 거기 못 가면 한 판을 통째로 날렸다.
> 2스테이지부터 1pt씩 붙어 **실패해도 뭔가 남는다.**

**환생 시 초기화되는 것**: 장수 · 장비 · 어빌리티 · 특성 · 재화 · 스테이지 진행 · 상점 · 이벤트 보너스
**남는 것**: 유물 트리 · 환생 포인트 · 도감 · 유저 정보 · 튜토리얼 기록 · 전투 설정 · 난이도 선택

정본: `Data/Sections/ReincarnationData.cs`, `Data/Core/UserDataManager.cs` (`Reincarnate()`가 초기화 목록의 정본)

### 6.2 유물 트리 — 69노드

환생 포인트로 찍는 영구 성장 트리. **5갈래 방사형**.

| 분기 | 위치 | 노드 수 | 내용 |
|---|---|---|---|

**해금 규칙**: 부모를 1레벨 이상 찍어야 자식이 열린다.
열리기 전에는 이름도 효과도 안 보이고, **보이는 노드의 자식만 "?" 실루엣**으로 그려진다.
→ 트리가 어디로 이어지는지는 알아야 지금 찍는 노드가 막다른 길인지 판단할 수 있다.

**시스템 효과 12종** (스탯이 아닌 규칙 자체를 바꾸는 노드)

| LoneWolfBonus | 트리로 **깎아낸** 병사 1명당 장수 공·체 +N% |

> **설계 노트 — 배속을 두 노드로 나눈 이유**
> 하나에 몰아 두면 첫 환생에 3배속이 열려 트리를 더 볼 이유가 사라진다.
> 저티어에서 2×, 고티어에서 3×.
>
> **설계 노트 — 장수 슬롯이 최종 티어가 아닌 이유**
> t3에 둔다. **부대 편성이 바뀌는 재미는 일찍 줘야 한다.**
>
> **설계 노트 — LoneWolf는 "현재 병사 수"가 아니다**
> "병사가 적을수록 강해진다"로 만들면 전멸 직전이 가장 센 판이 된다.
> 기준은 역분기 노드가 **깎은 고정 수치**다.

### 6.3 도감 (Codex)

**수집 = 영구 스탯 버프.** 만나 본 것을 기록한다.

|---|---|
| Equipment | 장비 |
| Ability | 어빌리티 |
| Trait | 특성 |

```
버프 = 수집 종수 × 0.5% (공격력·최대체력)
```

> ⚠ **버프는 여정 경계에서만 들어온다** (`LockForRun`).
> 런 시작 시 그때의 수집 수를 박아 두고, 런 중에 새로 채워도 이번 판에는 반영되지 않는다.
> 전투 중에 스탯이 계속 변하면 밸런스가 성립하지 않기 때문이다.
>
> 그래서 **환생 직후 "이번 여정 수확" 화면**을 띄운다 — 무엇을 채웠고 그 결과 얼마나
> 세졌는지를 한 화면에 편다. 이게 없으면 "갑자기 세졌는데 왜 세졌는지 모르는" 상태가 된다.

- **폭주 (Frenzy)** — 엘리트가 보스의 돌진을 습득, 보스가 분쇄 강타를 추가로 사용

> **설계 노트 — 난이도는 계수다**
> `StageConfig` 원본 값을 직접 바꾸지 않는다. 난이도를 되돌렸을 때 원래 값이 뭐였는지
> 알 수 없게 되기 때문이다. 난이도는 항상 곱해지는 계수로만 존재한다.

정본: `InGame/Difficulty/DifficultyConfig.cs`, `Editor/DifficultyConfigCreator.cs`

## 8. 기술 구조

### 8.1 ECS + Managed Bridge 혼합

```
ECS (Jobs/Burst) — 로직            Managed (MonoBehaviour) — 시각
────────────────────────           ──────────────────────────────
UnitAttackSystem                   UnitRuntimeBridge
UnitMovementSystem                 GeneralRuntimeBridge
UnitTargetSearchSystem             SoldierRuntimeBridge
UnitHitSystem                      EnemyRuntimeBridge
UnitStatusEffectSystem             UnitAppearanceBridge
GeneralSkillSystem
ActiveSkillAISystem      →  ActiveSkillExecuteSystem (managed)
ProjectileSystem         →  ProjectileView (managed)
PassiveSkillRuntimeSystem
CombatTriggerSystem
```

**핵심 패턴**: ECS가 로직을 돌리고, Managed Bridge가 시각·애니메이션을 동기화한다.

**왜 이렇게 나눴나**: 1,000마리 동시 전투가 요구사항이다. 타겟 탐색·이동·피격은
Burst 잡으로 돌려야 성립한다. 반면 스킬 실행(`Execute()`)은 프리팹 스폰·이펙트·사운드를
건드려야 해서 메인 스레드에서만 가능하다. 그래서 **판단은 ECS, 실행은 Managed**로 자른다.

### 8.2 전투 트리거 통합

장비·어빌리티·특성·패시브의 발동 효과를 **한 곳에서 디스패치**한다.

```
UnitDeathDespawnSystem (이벤트 발행)
        ↓ EnemyKillEvent · SoldierDeathEvent · …
CombatTriggerSystem (디스패치)
        ↓
장비 트리거 · 어빌리티 · 특성 · 패시브
```

> ⚠ **이벤트 버퍼를 비우는 것은 `CombatTriggerSystem` 뿐**이다.
> 먼저 도는 시스템이 지우면 트리거가 통째로 죽는다.

정본: `InGame/Skill/CombatTriggerSystem.cs`, `InGame/Skill/PassiveSkillComponents.cs`

### 8.3 발사체 예약 피해

발사체가 날아가는 동안 **예약 피해**(`IncomingDamage`)를 걸어 오버킬을 막는다.
이미 죽을 것이 확정된 적(`IsDoomed`)은 타겟 후보에서 빠진다.

> ⚠ **예약 피해와 실제 피해가 반드시 같은 값을 내야 한다.**
> 예약이 실제보다 크면 죽지 않은 적이 영영 타겟에서 제외되어 **전투가 멈춘다.**
> 두 곳 모두 `DamageMath.AfterDefense` 하나만 쓸 것.

### 8.4 세이브 구조

섹션별 분할 저장 (`ISaveSection`). 각 섹션이 자기 JSON을 직렬화한다.

| 섹션 | 환생 시 |
|---|---|
| UserData | 유지 |
| UnitData · ItemData · StageProgressData | **초기화** |
| EquipInventoryData · DeploymentData | **초기화** |
| RunAbilityData · RunTraitData · RunShopData · RunEventBonusData | **초기화** |
| RelicTreeData · ReincarnationData | 유지 |
| CodexData | 유지 (잠금만 해제) |
| BattleSettingsData · DifficultyData · TutorialData | 유지 |

> ⚠ `UserDataManager.Reincarnate()`의 초기화 목록이 **정본**이다. 새 섹션을 추가하면
> 여기 넣을지 말지를 반드시 결정할 것.
>
> ⚠ 튜토리얼·전투 설정은 초기화 목록에 넣지 않는다 — 환생마다 튜토리얼이 다시 뜬다.

### 8.5 오브젝트 풀

```
PoolType: UI=0, Unit=1, Effect=2, Projectile=3
```

`PoolController` 싱글턴 → `ObjectPool<T>` 관리. **`new` 대신 항상 `PoolController.Get()`**.

> ⚠ 이펙트 반납은 `EffectAutoReturn` 타이머인데 **`Time.timeScale`을 탄다.**
> 멈춘 사이 판이 끝나면 다음 판까지 남는다.

### 8.6 외형 합성 (PixelFantasy)

캐릭터 외형은 벤더 에셋(PixelFantasy)의 레이어를 런타임 합성한다.
**16 PPU · Point 필터** — 하드 픽셀 아트.

> ⚠ **전투 중 GC 주범은 `CharacterBuilder.Rebuild`**다. 공유 캐시를 얹어 해결했다.
> 벤더 에셋을 업데이트하면 우리 패치 3개가 통째로 날아간다:
> `CharacterBuilder.cs`(외형 공유 캐시) · `TextureHelper.cs`(머지 버퍼) · `Layer.cs`(mask 해시)

## 9. UI 원칙

전 UI가 **에디터 Creator 스크립트로 생성**된다. 프리팹을 손으로 고치지 않고 Creator를 고친 뒤 다시 굽는다.

### 필수 규칙 6가지

| # | 규칙 | 이유 |
|---|---|---|
| 1 | 누를 수 있는 버튼에는 **반드시 음각**을 넣는다 | 평평한 사각형은 버튼인지 라벨인지 구분이 안 된다 |
| 2 | 장식 기호에 **폰트 글리프를 쓰지 않는다** | 기본 폰트가 Static 250자라 없는 글자는 □로 나온다 (`★ ✔ ✕ ▶ ⚙` 전부 없음) |
| 3 | **반투명 테두리를 자식으로 두지 않는다** | Unity UI는 자기 Graphic → 자식 순으로 그린다. 자식은 부모보다 뒤로 못 간다 |
| 4 | 폰트 크기는 **`UIScale` 상수만** 쓴다 | 모바일 실기 기준. `FontSm`(34) 미만은 읽히지 않는다 |
| 5 | **칸 높이를 손으로 적지 않는다** | TMP 한 줄은 폰트의 약 1.25배. 작게 잡으면 아래가 잘린다 |
| 6 | 팝업 높이는 **1000px를 넘기지 않는다** | 로비 캔버스 세로가 1080뿐 |

### 크기 상수

```
폰트: FontSm 34 / FontMd 42 / FontLg 56 / FontXl 76
버튼: BtnSm 100 / BtnMd 132 / BtnLg 164
아이콘: IconSm 64 / IconMd 96
줄높이: Line(fontSize) = ceil(fontSize × 1.25)
최소 버튼 높이: BtnFor(fontSize) = ceil(fontSize × 1.7)
```

정본: `Assets/_project/1.Script/UI/UIScale.cs`, `Editor/EditorUIBuilder.cs`

## 10. 튜토리얼

**"언제 띄울지"는 `TutorialManager` 하나가 소유한다.** 각 UI가 제 자리에서 부르지 않는다.

**강제 진행 시나리오**
```
웨이브 개시 → Intro → InGame
승리       → BattleResult → Lobby → HeroStat
첫 환생 후 메인 화면 → FirstRelic (유물 트리 안내)
```

**도움말 시나리오** (팝업 헤더의 `i` 버튼) — 강제로 뜨지 않음
유물 · 어빌리티 · 장비 · 상점 · 이벤트 · 도감 · 난이도 · 장수 상세

### 규칙

- **팝업 위에서 시작하지 않는다.** 오버레이(sortingOrder 1000)가 팝업을 덮어 선택을 막는다.
  자기 무대 팝업(`StagePopup`) 하나만 떠 있는 경우만 예외.
- **예약 큐는 조건이 맞을 때까지 기다린다.** 단, **화면을 떠나면 버려야 한다** —
  안 그러면 출전 후 전투 중에 로비 튜토리얼이 뜬다.
- **패배는 중단(Abort)이되 완료로 치지 않는다.** 첫 판에 지고 환생했다고 튜토리얼을 본 것은 아니다.
- **환생을 한 번도 안 했으면 유물 안내를 띄우지 않는다.** 쓸 포인트가 0인 화면에서
  "여기서 강화하세요"는 설명이 아니라 광고다.
- 튜토리얼 기록은 **환생으로 초기화하지 않는다.**

정본: `Tutorial/TutorialManager.cs`, `Tutorial/Scenarios/`

## 11. 신규 프로젝트로 옮길 때 — 판단이 필요한 지점

이 절은 현행 설계의 기록이 아니라, **파생 기획 시 재검토할 후보 목록**이다.

### 11.1 검증된 것 (그대로 가져갈 만함)

| 항목 | 근거 |
|---|---|
| 30스테이지 고정 시퀀스 + 5의 배수 허들 | 리듬이 예측 가능하고 정비 타이밍이 보장된다 |
| 상점을 허들 직전에 고정 | 무작위 배치의 실패를 겪고 고친 결과 |
| 환생 포인트 후반 가중 곡선 | 평탄 곡선일 때 "초반에 죽고 다시 도는 것이 이득"이 됐다 |
| 최소 환생 스테이지 2 | 실패해도 뭔가 남아야 재시도 동기가 산다 |
| 도감 버프를 여정 경계에 고정 | 전투 중 스탯 변동은 밸런스가 성립하지 않는다 |
| 유물 트리의 안개 + 실루엣 | 막다른 길 판단을 위해 "어디로 이어지는지"만 노출 |
| 교환형 패시브 / 역분기 노드 | 순수 상향만 있으면 "좋은 걸 뽑았나"만 남는다 |
| 보스를 "느리고 무겁게" | 난전 밀도에서 보스를 읽히게 하는 유일한 방법이었다 |
| ECS 판단 / Managed 실행 분리 | 1,000마리 + 프리팹 스폰을 동시에 만족시킨다 |

### 11.2 재검토가 필요한 것

| 항목 | 문제 |
|---|---|
| **미사용 재화 4종** | Gem · Stamina · Honor는 획득처도 소비처도 없다. BattleStone은 폐지됨. 신규 프로젝트에서는 처음부터 넣지 말 것 |
| **Energy 소비** | 스테이지 입장에 에너지를 쓰는데, 런 기반 구조와 충돌한다 (런이 끊기는 지점이 애매) |
| **직업 4종의 좁은 폭** | 병사 수·지휘력이 Knight만 3~7 / 10~45이고 나머지 셋은 전부 1~2 / 1~30이다. 실질적으로 "병사 빌드 = 기사"로 고정된다 |
| **어빌리티 51종 / 특성 58종의 관리 비용** | enum + SO + 로직 3중 등록이 필요해 추가마다 누락이 발생한다 |
| **PvP (Honor)** | 설계에만 있고 구현 없음. 오토배틀은 비동기 PvP와 궁합이 좋으므로 초기 설계에 포함할지 결정할 것 |
| **아이콘 화풍** | 전장이 16 PPU 하드 픽셀인데 UI 아이콘을 고해상도 렌더링으로 만들면 충돌한다. 처음부터 픽셀 그리드로 통일할 것 |

### 11.3 구조적으로 다시 짤 만한 것

**① enum + SO + 로직 3중 등록**
스킬·특성·어빌리티를 추가할 때마다 enum, SO 에셋, 런타임 로직 세 곳을 손대야 한다.
누락이 잦다 (실제로 `ActiveSkillId` 20종짜리 문서 표가 실제 33종과 13종 어긋난 채로 남아 있었다).
→ **SO를 단일 정본으로** 삼고 enum을 생성하거나, 아예 문자열 ID + SO만으로 갈 것.

**② 프리팹 = Creator 산출물 규칙의 대가**
UI를 코드로 굽는 방식은 일관성·재현성이 좋지만, 디자인 이터레이션이 느리다.
Creator를 고치고 → 굽고 → PopupManager를 다시 로드해야 한 픽셀도 확인할 수 있다.
→ 레이아웃은 프리팹으로, **수치만 상수로** 빼는 절충안을 검토할 것.

**③ 두 씬 상주 모델**
전환은 빨라졌지만 "지난 전투의 흔적을 스스로 지워야 한다"는 부담이 모든 시스템에 생겼다
(`BattleArena`가 유닛·이펙트·발사체를 회수, `OnBattleWillPrepare` 이벤트로 각자 정리).
→ 유지할 가치는 있으나, **정리 책임을 한 곳에 모으는 설계**를 처음부터 넣을 것.
